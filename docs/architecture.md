# Architectural Vision

Ancestra is a modern, project-based genealogy application.

The primary goal is to provide a professional desktop experience for genealogy research while completely abstracting the underlying storage mechanisms from the user.

Users work with genealogy projects.

The database is an implementation detail.

The architecture follows the principle:

> Facts are stored. Views are generated.

The genealogy database stores facts only.

All visualizations, reports, trees, and numbering systems are dynamically generated by the genealogy engine.

---

# High-Level Architecture

Ancestra consists of five logical layers:

```text
Application Settings
        ↓
Project Configuration
        ↓
Genealogy Database
        ↓
Genealogy Engine
        ↓
Generated Views
```

Each layer has clearly defined responsibilities.

---

# Layer Responsibilities

## Application Settings Layer

Application settings are user-specific.

They define how Ancestra behaves for a particular user.

Examples:

- Language
- Theme
- Window layout
- User preferences
- Recently opened projects

Application settings are independent of any genealogy project.

They are stored separately from both projects and genealogy data.

---

## Project Configuration Layer

Projects represent the primary user-facing entity in Ancestra.

Users open projects rather than databases.

The project layer stores:

- Project metadata
- Database references
- Media locations
- Export locations
- Preferred root person
- Future project-level preferences

Projects are represented by a dedicated project file.

Example:

```text
MyFamily.ancestra
```

---

## Genealogy Database Layer

The genealogy database stores genealogy facts.

The database is implemented using SQLite.

The database contains:

- Persons
- Families
- Relationships
- Events
- Places
- Sources
- Media references
- Notes

The database does not store:

- Family trees
- Ancestor trees
- Descendant trees
- Reports
- Generated charts
- Kekulé numbers

The database stores a genealogy graph rather than genealogy views.

---

## Genealogy Engine Layer

The genealogy engine transforms stored facts into usable views.

The engine is responsible for:

- Graph traversal
- Relationship calculation
- Ancestor calculations
- Descendant calculations
- Relationship path discovery
- Dynamic Kekulé numbering
- Report generation
- Family card generation

The genealogy engine is the core business layer of the application.

---

## Generated Views Layer

Generated views are temporary representations created by the genealogy engine.

Examples include:

- Family trees
- Ancestor trees
- Descendant trees
- Family cards
- Relationship reports
- Search results
- Print layouts
- Exports

Generated views are never persisted as genealogy data.

---

# Project Architecture

Ancestra is a project-based application.

Users interact with projects rather than raw database files.

The project file is the primary entry point.

Example:


The project file is responsible for:

- Storing project metadata
- Storing the preferred root person
- Future project-specific configuration

The project file does not store genealogy facts.

# Genealogy Architecture

## Graph-Based Model

Ancestra stores genealogy data as a graph.

A genealogy graph consists of:

- Persons
- Family units
- Parent-child relationships
- Partner relationships

The graph serves as the foundation for all genealogy calculations.

---

## Dynamic Root Person

Any person can become the root person of a generated view.

Examples:

- Personal ancestry research
- Descendant analysis
- Family branch exploration
- Historical ancestor analysis

Changing the root person must never modify genealogy data.

Root-person selection is project configuration.

---

## Dynamic Kekulé Numbering

Kekulé numbers are generated dynamically.

The genealogy engine calculates them based on:

- The selected root person
- The genealogy graph

Kekulé numbers are:

- Computed values
- View-specific values
- Non-persistent values

No Kekulé number is stored in the database.

# Runtime Architecture

## Two-Process Model

Ancestra uses a two-process architecture provided by Tauri v2.

```text
┌────────────────────────────┐
│ Frontend                   │
│ TypeScript UI              │
│ WebView2 Sandbox           │
└──────────────┬─────────────┘
               │ IPC
               ▼
┌────────────────────────────┐
│ Backend                    │
│ Rust Core                  │
│ Genealogy Engine           │
│ Database Access            │
└──────────────┬─────────────┘
               │
               ▼
┌────────────────────────────┐
│ SQLite Database            │
└────────────────────────────┘
```

# Frontend Architecture

## Technology Stack

Frontend technologies:

- TypeScript
- HTML5
- CSS3
- Vite

The frontend is responsible for:

- User interaction
- State presentation
- Data visualization
- Navigation
- Form management

The frontend contains no direct database access.

---

## Frontend Principles

The frontend should emphasize:

- High usability
- Fast data entry
- Minimal navigation overhead
- Responsive workflows
- Large genealogy projects

Genealogy complexity should be handled by the backend rather than exposed through the user interface.

---

# Backend Architecture

## Technology Stack

Backend technologies:

- Rust
- Tauri v2
- rusqlite

The backend is responsible for:

- Project loading
- Database access
- Business logic
- Genealogy calculations
- Graph traversal
- Data validation
- File management

---

## Business Logic Location

All genealogy calculations belong to the backend.

Examples:

- Ancestor traversal
- Descendant traversal
- Relationship calculations
- Dynamic numbering systems
- Duplicate detection

The frontend must never become the source of genealogy logic.

---

# Database Architecture

## Technology

SQLite is used as the genealogy persistence layer.

Benefits:

- Local-first architecture
- High performance
- Simple deployment
- Excellent portability
- Transaction safety

---

## Storage Principle

The database stores genealogy facts only.

Examples:

- Person records
- Family records
- Relationships
- Events
- Sources

The following are intentionally excluded:

- Project settings
- Application settings
- Generated reports
- Tree layouts
- Kekulé numbers

---

# Communication Architecture

## Inter-Process Communication

Frontend and backend communicate exclusively through Tauri IPC.

The frontend invokes backend commands.

The backend performs:

- Validation
- Business logic
- Database operations

and returns structured results.

---

## Serialization

Data exchanged between TypeScript and Rust is serialized as JSON.

This provides:

- Strong interoperability
- Simplicity
- Predictable message formats

# Future Evolution

The architecture is designed to support future expansion while preserving the Version 1 principles.

Potential future additions include:

- Advanced reporting
- GEDCOM import
- GEDCOM export
- Additional visualization modes
- Plugin architecture
- Optional synchronization features

Future enhancements must not violate the core architecture:

> The genealogy database stores facts, not views.

> Ancestra is a project-based genealogy application, not a database application.

> Facts are stored. Views are generated.
